Datenbank-Update schlägt fehl (Collations)

Letzte Änderung 04.11.2026 · Version 4 · Seiten-ID 730

Ein Update bricht mit einer Meldung über gemischte Sortierreihenfolgen ab.

Symptom

Text
Illegal mix of collations (latin1_swedish_ci,IMPLICIT) and (latin1_german1_ci,IMPLICIT) for operation 'like'

Die Meldung tritt beim Datenbank-Update auf, wenn zwei Tabellen verglichen werden, deren Textspalten unterschiedliche Sortierreihenfolgen tragen.

Das Problem kann nur bei großen Updateschritten von sehr alten Versionen auftreten, z. B. von 5.13, 5.16 oder älter.

Ursache

Ältere Tabellen wurden ohne ausdrückliche Sortierreihenfolge angelegt und haben deshalb den MySQL-Standard latin1_swedish_ci. Neuere Tabellen tragen latin1_german1_ci.

Betroffen ist typischerweise die Tabelle ipos_changehistory_log: Sie wurde mit ENGINE=MyISAM DEFAULT CHARSET=latin1 ohne Collation angelegt, ihre Spalte REMARKS steht damit auf latin1_swedish_ci. Beim Update wird sie mit ipos_tse_instance verglichen, deren Spalte PUBLIC_KEY auf latin1_german1_ci steht — der Vergleich scheitert.

Die auslösende Anweisung des Updates legt eine temporäre Tabelle an und verknüpft dabei die Änderungshistorie über LIKE mit den öffentlichen Schlüsseln der technischen Sicherheitseinrichtungen (TSE):

SQL
... FROM ipos_changehistory_log his
JOIN (SELECT DISTINCT PUBLIC_KEY FROM ipos_tse_instance WHERE PUBLIC_KEY IS NOT NULL) public_keys
ON his.REMARKS LIKE CONCAT('%', public_keys.PUBLIC_KEY, '%')
WHERE REMARKS LIKE '%Certificates%' ...

Welche Sortierreihenfolge eine Tabelle tatsächlich verwendet, zeigt:

SQL
SHOW FULL COLUMNS FROM ipos_changehistory_log;
SHOW FULL COLUMNS FROM ipos_tse_instance;

Lösung

Die Tabelle dauerhaft auf die richtige Sortierreihenfolge umstellen:

SQL
ALTER TABLE ipos_changehistory_log CONVERT TO CHARACTER SET latin1 COLLATE latin1_german1_ci;

Danach prüfen:

SQL
SHOW FULL COLUMNS FROM ipos_changehistory_log;

Die Spalte REMARKS muss jetzt latin1_german1_ci zeigen. Anschließend das Update erneut starten.

Behelf für den Einzelfall

Lässt sich die Tabelle im Moment nicht umstellen, kann die Sortierreihenfolge in der Abfrage erzwungen werden — an beiden Stellen, an denen REMARKS verglichen wird:

SQL
... ON his.REMARKS COLLATE latin1_german1_ci LIKE CONCAT('%', public_keys.PUBLIC_KEY, '%')
... WHERE REMARKS COLLATE latin1_german1_ci LIKE '%Certificates%'

Wird nur eine der beiden Stellen angepasst, tritt derselbe Fehler an der anderen auf. Das behebt den Einzelfall, nicht die Ursache — beim nächsten Update tritt der Fehler wieder auf.

Zu beachten

Vor jedem Eingriff an der Datenbankstruktur eine Sicherung anlegen. Ein ALTER TABLE auf einer großen Protokolltabelle kann längere Zeit laufen; führen Sie ihn außerhalb der Geschäftszeiten aus.

Tritt der Fehler auf weiteren Tabellen auf, gilt derselbe Weg: Alle Textspalten der betroffenen Tabellen auf latin1_german1_ci vereinheitlichen.
