Datenbank sperrt Host (many connection errors) beheben

Letzte Änderung 15.10.2026 · Version 3 · Seiten-ID 866

Die Kassen synchronisieren nicht mehr, weil der Datenbankserver der Zentrale alle Verbindungen von der öffentlichen IP-Adresse der Filiale ablehnt.

Symptome

  • Im Synchronisationsfenster der Kasse unter Letzte Synchronisation: java.sql.SQLException: null, message from server: "Host '<IP>' is blocked because of many connection errors; unblock with 'mariadb-admin flush-hosts'".
  • Der Verbindungstest an der Kasse bricht mit derselben Meldung ab.
  • Alle Kassen eines Standorts sind gleichzeitig betroffen.

Mögliche Ursachen

MariaDB zählt je Absender-IP die Verbindungsversuche, die vor Abschluss der Anmeldung abbrechen. Übersteigt der Zähler max_connect_errors (Standard 100), sperrt der Server diese IP, bis der Host-Cache geleert wird. Eine erfolgreiche Anmeldung setzt den Zähler zurück; ein falsches Passwort zählt nicht.

Alle Kassen hinter demselben Internetanschluss teilen sich eine öffentliche IP-Adresse – deshalb werden sie gemeinsam gesperrt.

Typische Auslöser abgebrochener Verbindungsversuche:

  • instabile Verbindung oder Paketverluste zwischen Filiale und Zentrale
  • Abbruch beim SSL-Handshake, siehe ITR Partner Service → Betrieb & Administration → Datenbankbenutzer und SSL
  • Zeitüberschreitung beim Verbindungsaufbau
  • Monitoring, Portprüfungen oder andere Geräte am Standort, die den Datenbankport öffnen, ohne sich anzumelden

Lösung

  1. Ursache eingrenzen, solange die Sperre besteht – das Aufheben der Sperre löscht diese Daten:

    SQL
    SELECT IP, SUM_CONNECT_ERRORS, COUNT_HANDSHAKE_ERRORS, COUNT_SSL_ERRORS,
       FIRST_ERROR_SEEN, LAST_ERROR_SEEN
FROM performance_schema.host_cache
WHERE IP = '<öffentliche IP der Filiale>';
SHOW GLOBAL STATUS LIKE 'Aborted_connects';

    Viele COUNT_SSL_ERRORS → SSL-Konfiguration prüfen. Viele COUNT_HANDSHAKE_ERRORS → Netzwerkstrecke und Geräte am Standort prüfen, die den Port ansprechen.

    Liefert die Abfrage nichts, prüfen, ob performance_schema aktiv ist: SHOW GLOBAL VARIABLES LIKE 'performance_schema';. Ist der Wert ON, die eingetragene IP prüfen. Ist er OFF (Standard bei MariaDB): in der Serverkonfiguration (my.cnf / my.ini) im Abschnitt [mysqld] die Zeile performance_schema=ON eintragen und den Datenbankdienst neu starten. Die Einstellung lässt sich nicht zur Laufzeit ändern. Der Neustart unterbricht die Verbindung aller Kassen und des CentralPoint – außerhalb der Geschäftszeiten durchführen. Die Auswertung ist erst bei der nächsten Sperre möglich.

  2. Sperre aufheben auf dem Datenbankserver der Zentrale:

    BASH
    mariadb-admin -u root -p flush-hosts

    alternativ per SQL:

    SQL
    FLUSH HOSTS;

  3. Ergebnis prüfen: an einer Kasse den Verbindungstest ausführen oder die Synchronisation von Hand auslösen, siehe ITR Partner Service → Produkte → Daten von Hand synchronisieren.

  4. Optional Grenzwert erhöhen, damit einzelne Störungen nicht sofort zur Sperre führen. Behebt nicht die Ursache.

    SQL
    SET GLOBAL max_connect_errors = 10000;

    Dauerhaft in der Serverkonfiguration im Abschnitt [mysqld] eintragen: max_connect_errors=10000.

Protokolldateien

  • Kasse: itrcr_Syncer_*.log und spring.log unter C:\GoodCompany\Kasse\log\
  • Datenbankserver: Fehlerprotokoll von MariaDB, Einträge Aborted connection bzw. Aborted connect von der gesperrten IP

Informationen für den Support

  • öffentliche IP-Adresse der Filiale und betroffene Kassen
  • Zeitpunkt der letzten erfolgreichen Synchronisation
  • Ausgabe der Abfrage auf performance_schema.host_cache
